# 创意导演统一入口设计

> 状态：已由用户确认
>
> 日期：2026-07-26
>
> 范围：需求收敛、参考图要素借用、模型研究、十三块拆解预览

## 1. 背景

Anima Prompt Studio 当前按文生图、图生图及结构化编辑能力组织功能，但用户的真实起点
通常不是一个完整任务类型，而是零散灵感：

- 不知道具体画什么；
- 只有动作、环境、服装等局部想法；
- 上传参考图后只想借用其中某个要素；
- 希望系统主动补全创意，但不能擅自改变已经确认的内容。

因此，首页不应要求用户先判断“文生图还是图生图”。产品应先帮助用户明确“想画
什么”，再把确认后的创作意图转化为模型适配的结构化提示词。

## 2. 产品目标

建立一个统一的“创意导演”入口。用户可以输入零散文字、上传一张或多张参考图，
由系统先提出创意草案，再通过导演式追问收敛需求，生成可确认的画面需求单。确认后，
用户选择目标基础模型，系统根据有证据的模型档案生成十三块拆解预览，最后进入现有
结构化工作台。

产品成功需要同时满足两项标准：

1. 系统理解的画面与用户心中的目标高度一致。
2. 拆解和最终配方针对所选模型进行了可靠、可解释的适配。

丰富度和对话速度是次要指标，不能以牺牲意图保真为代价。

## 3. 非目标

首版不包含：

- ComfyUI 自动出图；
- 完整 LoRA 自动研究和复杂兼容性推理；
- 面向陌生用户的教程、注册、云同步或多人协作；
- 用模型偏好自动改写用户已经确认的创作意图；
- 把自由聊天记录直接当作唯一状态来源。

## 4. 核心流程

```text
零散文字 / 一张或多张参考图
  → 创意导演理解输入
  → 一个主方案 + 两个简短替代方向
  → 自适应导演式追问
  → 画面需求确认单
  → 选择目标基础模型
  → 读取或建立模型档案
  → 模型适配的十三块拆解预览
  → 用户确认拆解
  → 现有结构化工作台
  → Anima 完整配方
```

首页只有一个统一创作入口，不再要求用户选择文生图或图生图。图片是创作意图的证据
和参考来源，不是单独的产品模式。

### 4.1 首页输入

首页中央提供：

- 对话输入框；
- 单图和多图上传；
- 拖拽上传；
- 每张图片的用途说明；
- 当前任务的本地模型或外部 API 选择。

用户可以主动指定每张图片的借用范围，例如：

- 图 1：只借用动作；
- 图 2：借用服装；
- 图 3：借用环境和光影。

若用户没有指定，系统先分析图片，列出可借用的人物、外观、服装、动作、环境、构图、
光影和风格等要素，再请用户确认。未被选择的图片内容不得进入后续需求或提示词。

多图属于目标能力。交付时可先完成单图全流程，再接入多图组合，但单图实现的数据结构
和接口不得阻碍多图。

### 4.2 创意方向

当输入不足以形成完整画面时，系统默认提供：

- 一个推荐的完整主方案；
- 两个明显不同但简短的替代方向。

用户选定方向后，系统继续细化。系统不应一次生成大量候选，也不应在提出任何方案前
把所有缺失细节逐项询问一遍。

### 4.3 自适应追问

追问遵循以下节奏：

- 会显著改变题材、主体、叙事或画面方向的问题，每轮只问一个；
- 服装细节、光影、镜头等关联小项可以合并询问；
- 每轮允许用户回答“交给你决定”“跳过”或直接修改此前结论；
- 不询问对成图影响很小、可安全补全的细节；
- 创意阶段以创意为主，不受 Anima 提示词语法束缚；
- 若要求明显难以生成或不稳定，提前说明风险，但不擅自修改。

当主体、核心动作或状态、主要环境和视觉方向已经基本明确时，系统可以生成画面需求
确认单。其他细节可以由 AI 补全，但必须标明来源。

## 5. 创意导演 Skill

创意导演不是通用聊天机器人，而是有稳定输出约束的需求收敛器。

### 5.1 行为规则

- 先复述理解，再提出补全或问题。
- 明确区分用户要求、图片证据和 AI 推测。
- 已确认内容默认锁定。
- 新要求与锁定项冲突时，说明冲突并取得用户同意后才能修改。
- 信息不足时先给可选创意，不把流程变成连续问卷。
- 不直接生成最终提示词；先完成创作意图确认。
- 模型偏好只能影响表达和参数，不能覆盖确认后的语义。

### 5.2 Skill 管理

系统提供一个内置、稳定的“总导演” Skill。高级设置允许用户：

- 查看当前 Skill；
- 修改个人覆盖版本；
- 恢复内置默认版本。

用户覆盖可以改变导演风格和提问策略，但不能移除结构化输出、来源标记、冲突检查和
锁定保护。覆盖版本损坏或输出不合法时，系统不得写入正式状态。

### 5.3 结构化输出

每轮模型响应至少包含：

- 当前完整画面草案；
- 用户明确项；
- 图片借用项及来源图片；
- AI 补全项；
- 锁定项；
- 冲突项；
- 待确认项；
- 建议提出的下一个问题；
- 当前是否已具备生成需求单的条件。

对话文本是展示层，结构化状态才是后续流程的事实来源。

## 6. 画面需求确认单

第一阶段结束时，系统生成一张易读的需求确认单，而不是直接生成最终提示词或十三块。

确认单包含：

- 完整的自然语言画面描述；
- 用户明确要求；
- 每张参考图实际借用的要素；
- AI 主动补全的内容；
- 已锁定、不得静默修改的内容；
- 尚未确定的内容；
- 仍存在的冲突或生成风险。

只有用户主动确认后，流程才能进入模型选择和拆解阶段。

返回修改需求单时，已有拆解和最终配方统一标记为过期。系统不得把新需求与旧提示词
混合使用。

## 7. 模型选择与研究

模型选择发生在画面需求单确认之后、十三块拆解之前。系统可以预选上次使用的模型，
但用户可以更换。

### 7.1 基础模型档案

用户可以粘贴模型的原始页面链接。系统读取原始页面，并在必要时检索补充资料，生成
待审核的基础模型档案。

档案包含：

- 模型名称、类型和精确版本；
- 原始页面链接；
- 推荐的提示词语言与语法；
- 必需或推荐的前缀、质量词和触发词；
- 不推荐或无效的写法；
- 正向和负向提示词特点；
- 推荐采样器、调度器、Steps、CFG 和尺寸；
- 模型擅长与薄弱的题材、构图和风格；
- 已知限制和注意事项；
- 页面抓取时间；
- 用户审核状态；
- 本地实测记录。

每条研究结论必须归入以下一种证据类别：

1. 原始模型页面明确说明；
2. 其他补充资料提供的信息；
3. AI 根据资料作出的推断；
4. 用户本地实测结论。

系统不能把补充资料、AI 推断或社区经验标记为官方结论。

### 7.2 不完整资料

若页面无法读取或资料不足，系统建立“待验证档案”：

- 只自动应用有明确证据的规则；
- 其余内容使用通用规则；
- 清晰提示哪些优化尚未验证；
- 允许用户手工补充资料和结论；
- 不因研究失败阻塞整个创作流程。

### 7.3 LoRA 首版边界

首版 LoRA 只保存：

- 名称和版本；
- 原始链接；
- 触发词；
- 建议权重；
- 用户备注；
- 简单的兼容或冲突记录。

完整 LoRA 资料研究、自动组合推荐和复杂冲突分析不属于本规格首版。

## 8. 十三块拆解预览

模型档案确定后，系统生成拆解预览：

1. 人物身份
2. 外观特征
3. 服装配饰
4. 表情
5. 姿势动作
6. 人物互动
7. 场景环境
8. 构图镜头
9. 光影色彩
10. 风格与艺术家
11. 道具特效
12. 质量增强
13. 负向约束

每个结构块展示：

- 中文语义；
- 针对目标模型优化后的英文表达；
- 内容来源；
- 锁定状态；
- 模型适配理由；
- 风险或未经验证的规则。

用户可以逐块接受、修改或退回。全部确认后才进入现有结构化工作台。

### 8.1 两层优化

拆解明确分为两层：

- 语义层：忠实表达确认后的画面需求；
- 模型层：调整词序、语法、质量词、触发词、负向词和生成参数。

模型层不得改变语义层。若目标模型不擅长某项要求，系统只能提出风险和替代建议，
是否修改需求由用户决定。

切换目标模型时，需求单保持有效，旧拆解和配方失效并重新生成。

## 9. 数据与状态

每次创作保存完整链路：

```text
原始文字和图片
  → 对话记录
  → 结构化导演状态
  → 画面需求单
  → 锁定项和来源关系
  → 模型档案及版本
  → 十三块拆解
  → 最终配方版本
```

刷新、关闭或重开项目后，用户可以从已确认阶段继续。系统不能仅依赖模型上下文恢复
状态。

参考图片需要稳定 ID。每个借用项记录图片 ID、要素类型和用户确认状态，以支持多图
来源追溯。

模型档案必须版本化。历史配方继续引用生成当时使用的档案版本，后续网页研究更新不能
静默改变旧作品。

## 10. 外部 API 与隐私

设置中可以选择默认推理策略，并允许每次任务临时切换本地模型或外部 API。

- 纯文字是否自动发送遵循用户的默认策略；
- 发送图片到外部 API 时必须有明显提示；
- 不得在失败时静默切换到另一个外部提供商；
- API Key 继续遵守现有本地保存和不回显规则；
- 外部调用失败不得丢失已确认状态。

## 11. 异常处理

- 外部 API 失败：保留当前状态，可重试或切换服务。
- 单张图片分析失败：标出失败图片，不丢弃其他图片结果。
- 模型网页无法读取：允许手工补充，保持“待验证”状态。
- 模型输出格式错误：不写入正式状态；可自动尝试一次结构修复，仍失败则保留上一
  有效版本并提示用户。
- 锁定项冲突：暂停相关修改，取得确认后继续。
- 切换模型：使拆解和配方过期，不改变需求单。
- 修改需求单：使所有下游产物过期。
- 异步结果迟到：沿用当前工作区修订保护，不得覆盖更新后的需求或拆解。

## 12. 组件边界

建议将能力分成可独立测试的单元：

- **统一输入控制器**：管理文字、图片、用途指定和任务推理提供商。
- **图片要素分析器**：输出候选要素及证据，不决定用户最终借用范围。
- **创意导演引擎**：运行 Skill，维护结构化状态、锁定项和下一个问题。
- **需求单管理器**：生成、确认和版本化画面需求。
- **模型研究器**：抓取原始页面、补充研究、证据分级和生成待审核档案。
- **模型档案库**：保存版本化基础模型和简化 LoRA 档案。
- **模型适配拆解器**：将确认语义映射为十三块并应用已验证模型规则。
- **阶段状态机**：负责确认门禁、过期传播、恢复和错误回退。

这些组件可以接入现有 `prototype/server.py`、`prototype/db.py`、Recipe 和模型档案能力，
但本规格不预先规定具体表名和 API 路径；实施计划阶段应先审计现有接口并最小化迁移。

## 13. 测试与验收

### 13.1 功能验收

- 首页不要求选择文生图或图生图。
- 文字、单图和多图进入同一导演流程。
- 用户可以指定每张图的借用要素。
- 未指定用途时，系统提出图片要素建议并等待确认。
- 系统给出一个主方案和两个简短替代方向。
- 追问节奏能按问题影响程度自适应。
- 已确认内容不会被静默修改。
- 系统能生成并确认画面需求单。
- 用户能在拆解前选择基础模型。
- 原始链接能生成带证据等级的待审核模型档案。
- 资料不足时仍能使用通用规则继续，但必须明确警告。
- 系统能生成模型适配的十三块拆解预览。
- 拆解确认后能进入现有工作台。
- 切换模型或修改需求时，下游结果正确过期。
- 刷新和重开后能够恢复当前阶段。

### 13.2 质量验收

准备覆盖以下输入的固定案例：

- 只有一个动作；
- 只有环境和情绪；
- 只有服装；
- 文字加单张图片，并只借用动作；
- 多图分别借用动作、服装和环境；
- 新要求与锁定项冲突；
- 模型页面完整；
- 模型页面不完整或不可访问；
- 中途切换基础模型；
- 外部 API 和图片分析部分失败。

每个案例分别评估：

1. 意图保真：最终需求单是否准确反映用户选择；
2. 来源准确：用户、图片、AI 和模型规则是否正确标记；
3. 锁定可靠：确认项是否在后续流程中保持不变；
4. 模型适配：英文表达和参数是否只使用相应档案中允许应用的规则；
5. 可恢复性：失败、刷新和重开是否保留最近有效状态。

自动测试使用 mock provider 和固定网页夹具，不依赖真实外部 API 或实时网页。

## 14. 实施切分

本设计涉及多个可独立交付的子项目，实施计划应按以下顺序拆分：

1. 阶段状态、需求单、来源和锁定的数据基础；
2. 统一首页与单图创意导演闭环；
3. 多图用途指定和来源追溯；
4. 基础模型链接研究与版本化档案；
5. 模型适配的十三块拆解预览；
6. 简化 LoRA 档案；
7. 完整恢复、回归和真实 Anima 出图验收。

每个子项目独立形成实施计划和验收结果，避免同时重写首页、数据层、模型研究和拆解
引擎。
